A task's home in memory

We created one FreeRTOS task and gave it a 2048-byte stack. The debugger says 2040. Where did 8 bytes go? To find out, we follow the task through the memory cupboard of an STM32, shelf by shelf: who puts what where, and when. Every number was measured on a real board. New to memory? Questions I asked on the way

About the task's memory

Each shelf is one byte. What is the label of the last RAM shelf?

Last = first + number of shelves − 1. 128 KB = 131,072 = 0x20000 shelves, so 0x20000000 + 0x20000 − 1 = 0x2001FFFF. The address 0x20020000 is one past the end; the main stack starts there.

Are the memory compartments placed directly below each other?

No. Between them is wall: addresses with no memory behind them. Touching one gives a HardFault. The order in the linker script's MEMORY block doesn't matter; the addresses decide.

After .data ends, does .bss start? And then ucHeap?

.bss starts right after .data (0x20000070). But ucHeap does not come after .bss: it is one variable inside it, with other variables before and after it.

Is there one ucHeap per task?

One for the whole program. Every task and queue that FreeRTOS creates dynamically is cut out of the same array.

Does the linker place the task's stack?

No. The linker doesn't know tasks exist. It places the empty box. osThreadNew → pvPortMalloc cuts the stack out of it while the program runs. That's why the map file shows ucHeap but never "defaultTask stack".

Are the 8 header bytes taken from my 2048?

No, they are extra. pvPortMalloc(2048) takes 2,056 bytes from the heap. The stack gets all 2048.

If the variables before the heap end at 0x20000002, does the stack start at 0x20000003?

No. heap_4 first rounds its start up to a multiple of 8 (0x20000008), then puts the 8-byte header there. The stack would start at 0x20000010.

Does an 8-bit variable use a whole 4-byte row of the stack?

Memory is byte-addressed; rows are only a drawing. Saved registers always take whole words. Small locals often stay in registers, and on the stack the compiler may pack four bytes into one word, or add padding.

Is it "multiple of 8" because the CPU reads 64 bits at a time?

No. The reason is the ARM calling standard (AAPCS): 8-byte values like double and uint64_t must sit on 8-byte boundaries. A wrong alignment breaks things like printf("%f"). The bus width only changes speed.

Must SP always be a multiple of 8?

At every function call and on every interrupt entry, yes (the CPU re-aligns on interrupts by itself). Inside a function it may briefly be only a multiple of 4.

Related questions

Are the task's attributes stored in RAM?

They are const, so they stay in Flash (.rodata). osThreadNew reads them once and copies what it needs into the TCB.

Are the Idle task and the timer task also in ucHeap?

Not in our setup. With static allocation enabled, their TCBs and stacks are fixed arrays in .bss, and so is the timer queue.

Where do interrupt handlers keep their data?

On the main stack (MSP) at the top of RAM. Tasks use the other stack pointer (PSP) and their own stacks. When an interrupt hits a task, the hardware still pushes its 8-word frame onto the task's stack first.

Is the .elf file stored in Flash?

No. Flash holds the program's contents: vector table, code, constants, starting values. The .elf with its debug information stays on the laptop.
