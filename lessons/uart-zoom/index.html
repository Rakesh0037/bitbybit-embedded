Who sets what

WhoSetsNever does
CPU (your code and HAL) All configuration: clocks, pins, BRR, UE, TE, the DMA job card (NDTR, M0AR, PAR, EN, interrupt enables), DMAT, TXEIE, TCIE. Inside a bell: clears flags, switches DMAT off and TCIE on, calls your callback. Watch TXE or TC while DMA or interrupts do the work. Clear TXE by hand: writing TDR clears it.
UART hardware TXE (mailbox empty), TC (wire quiet), TEACK. Moves the mailbox letter to the conveyor. Raises "TXE AND DMAT" as a DMA request and "TXE AND TXEIE" or "TC AND TCIE" as its interrupt line. Know how many letters are left. Call a function.
DMA hardware Copies one byte per request, counts NDTR down, moves its memory pointer. Sets HTIF at half, TCIF at the end, then switches its own EN off. Change UART bits. Check "count = 0" when a request comes: it counts after each copy.
NVIC (inside the CPU core) Turns a ringing line into "CPU, jump to this handler now". Know about Cplt. It only knows line numbers, like "USART3".

Questions I asked on the way

About this DMA send

Who sets TXE, and does someone have to watch it?

The UART hardware sets TXE whenever its mailbox (TDR) is empty. It is a flag, not a message: it stays 1 until something writes into TDR. Nobody has to stand next to it. It is like the flag on a mailbox.

Does the CPU clear TXE after writing a letter?

No. Writing into TDR clears TXE automatically, in hardware.

When exactly does TXE come back to 1?

When the waiting letter moves from the mailbox onto the conveyor (shift register), which is the moment its start bit begins. Not when its stop bit ends. That is why the UART always stays one letter ahead: while B is on the wire, l already waits in the mailbox.

The CPU sets TXEIE or DMAT. Who reads those bits?

The UART. Its own logic checks "TXE AND TXEIE" (then it raises its interrupt line to the NVIC) and "TXE AND DMAT" (then it raises a request wire to the DMA). The CPU only writes those bits.

When B moves to the conveyor, does the UART first ask for l, or first send B?

Both at the same time. The transmitter (shifting bits out) and the request logic are separate pieces of hardware working in parallel. l arrives a few clock cycles after B's start bit begins, then waits 87 µs.

What is a "handler"? Isn't it just CPU and UART?

A handler is only a function, like USART3_IRQHandler. When a line rings, the NVIC (part of the CPU core, its "ear") makes the CPU jump to that function. The CPU runs it and goes back to what it was doing.

I ticked the interrupt in CubeMX. Isn't that enough?

An interrupt needs two switches: the NVIC line enabled (done once at init, from your CubeMX tick) and the source enabled in the UART (TXEIE or TCIE, set by HAL for each send). One without the other rings nothing.

Is TC always 1?

TC is 1 whenever the wire is quiet: after reset, between messages, after the last stop bit. Writing a letter into TDR (or software writing TCCF) clears it. During a message it stays 0, because a next letter is always already waiting. That is why HAL switches TCIE on only at the very end.

Does TC depend on DMAT?

No. The UART sets TC whenever the last stop bit has left and nothing waits in the mailbox, with or without DMA.

Does the DMA switch DMAT off and TCIE on when it is done?

No, the DMA cannot touch UART bits. It rings the CPU (transfer complete); inside that bell, HAL's UART_DMATransmitCplt on the CPU switches DMAT off and TCIE on.

Does the DMA check "count = 0" when a request comes?

No. It counts NDTR down after every copy. When NDTR reaches 0 the job is finished: it sets TCIF, rings, and switches its stream off. That happens when \n is copied, while \r is still on the wire.

Does the NVIC call Cplt?

The NVIC only knows "the USART3 line is ringing". The chain is UART (TC AND TCIE) → NVIC → USART3_IRQHandler → HAL_UART_IRQHandler → HAL_UART_TxCpltCallback → your tx_done = 1.

With interrupts or DMA, which UART flag does the CPU monitor?

None. Hardware does the watching. Our loop only watches tx_done, our own variable in RAM, and only so we can measure. A real program would do other work.

Related questions

With polling (printf), does the CPU write l as soon as TXE is back?

Not with our __io_putchar: it sends one letter per call and HAL waits for TC before returning. So the wire goes quiet for a moment between letters. Sending the whole buffer in one call would only wait for TXE between letters, and for TC once at the end.

After \n, does _write look into the buffer and find it empty?

No. printf calls _write(file, ptr, len = 10); its loop counts to 10, then returns. The C library collects text until \n (line buffering) and then calls _write once with the whole line.

Is the letter stored in the status register?

No. The status register (ISR) only holds flags like TXE and TC. The letter goes into TDR.

Does the UART need the CPU to send bits?

It needs a clock, not the CPU: 130 MHz ÷ 1128 = one bit every 8.68 µs. The CPU could even sleep meanwhile.

Does the ST-LINK flash the chip over this UART?

No. Flashing uses separate SWD wires (SWDIO, SWCLK). The UART only carries your text to the ST-LINK, which passes it to the laptop as a serial port.
